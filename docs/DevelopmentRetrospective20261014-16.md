## 三、典型问题的定位与修复过程

### 1. 光效不贴真实屏幕，还有红条

**现象。** 初版颜色和预览切换能工作，但光效画在内容安全区或预览卡内。用户反馈“不适配屏幕、有红色条、效果不明显”，明确要求真实屏幕边缘向中心渐变并呼吸。

**怎么查。** 借助 `deveco-cli` 检索并读取安全区资料，历史记录保留了命令：

```sh
devecocli docs search "expandSafeArea" "Canvas createLinearGradient" --limit 6
devecocli docs read FAQ/UI框架/组件使用/expandSafeArea常见问题/faqs-arkui-1103
```

关键知识是：组件边界扩展到系统栏，不等于 Canvas 内部绘制自动覆盖到系统栏；百分比高度、父容器约束与绘制尺寸需要分别核对。FAQ 明确包含“Canvas 已扩展，但绘制内容不到底部导航条”的场景。

**怎么改。** 主窗口使用全屏布局与透明系统栏；从实际窗口取得尺寸并监听变化；把光效放到根部独立宿主中，使用 `LayoutPolicy.matchParent`、`ignoreLayoutSafeArea`。正文继续正常避让系统区域。唯一透明 Canvas 用四个不重叠区域绘制四边向中心渐隐，替换旧窄条与动态硬框。光效层触摸穿透，隔离预览复用同一层。

**怎样确认。** 控件树曾仍显示从 y146 开始，不能仅凭该值认定顶部没有画到。后续用截图像素、真机走查交叉确认物理四边覆盖和中心透明。10月15日完成约定的深浅色、静态／动态、切页取消和相册截图验收。光效回归最终24组通过，包含506次绘制和4,851次分区探测。

**Skill／知识库的贡献。** Skill 组织检索与验证流程；安全区 FAQ 直接帮助修正“扩展组件就等于扩展画布内容”的假设。最终几何和视觉是否正确由测试及手机证据确认。

证据：[暗色匹配过程记录](../暗色匹配。md) 第194—233行；[低分提醒验收](LowScoreReminder.md) 第113—159行。光效宿主安全区设置：`entry/src/main/ets/pages/Index.ets:2245`（`low-score-glow-host`）；画布尺寸处理：`entry/src/main/ets/components/LowScoreEdgeLight.ets:193`。

### 2. 静态细框消失：API 写入成功，读回来却是 undefined

**现象。** 深色动态光效能显示，但打开“减少动态效果”后，预期的静态细框不可见。先排除了开关状态和点击定位问题。

**定位结果。** 真机临时日志发现，对 `ctx.lineWidth` 赋值后，getter 返回 `undefined`。旧实现又读取这个属性计算描边的 inset、宽高，结果产生 NaN 坐标，细框无法正常绘制。

**修复。** 把需要的宽度保留为局部值，同时用于 API 设置和几何计算：

```ets
const lineWidth = strong ? 2 : 1.5;
ctx.lineWidth = lineWidth;
const inset = lineWidth / 2;
ctx.strokeRect(inset, inset, width - lineWidth, height - lineWidth);
```

**验证。** 增加只有 setter、不能读回有效宽度的 Canvas 桩，检查绘制坐标仍为有限数。后续走查确认四边约5—6px细框可见，并覆盖关闭、重开及恢复动态；临时诊断日志随后移除。

**Skill／知识库的贡献。** 这是设备运行证据驱动的修复，没有证据说明某个 skill 或官方 FAQ 事先给出了该 getter 异常的答案。技能提供规范与检查流程，具体原因靠日志和最小回归定位。

证据：`docs/WorkCheckpoint.md:90`；修复位置：`entry/src/main/ets/components/LowScoreEdgeLight.ets:168`；回归：`scripts/verify-edge-light.cjs:697`。

### 3. 深浅色与 Canvas 颜色解析：资源、UI 作用域、重绘要配合

**问题。** 光效不能对所有主题固定使用同一个浅色红；Canvas 解析资源时还需明确 UI 实例。只切换系统模式或改变开关，不能代替资源更新和画布重绘。

**处理。** 复用已有系统主题跟随机制，在 `base/element/color.json` 与 `dark/element/color.json` 中增加同名低分颜色资源。Canvas 通过 `ColorMetrics.resourceColor` 解析，在 `getUIContext().runScopedTask` 内执行；主题变化触发重画。异常回退分别匹配深浅色与提醒等级，避免一级也回退为增强色。

**知识来源与时机。** 历史记录明确说明，《应用深浅色适配》是在用户要求说明过程后检索、阅读全文，用来核对已采用的机制；不能倒写成它自动生成了最初配色。历史命令为：

```sh
devecocli docs search "深色模式" "dark目录" --limit 6
devecocli docs read 开发指南/ArkUI_方舟UI框架/UI开发_ArkTS声明式开发范式/主题设置/应用深浅色适配/ui-dark-light-color-adaptation
```

原始日志进一步确认：10月14日19:34:06搜索 `runScopedTask`，19:34:40读取 UIContext 模块说明，19:35:42修改光效组件与回归脚本。该说明解释了未绑定 UI 上下文的异步回调可能无法确定 UI 实例，`runScopedTask` 可在指定实例作用域执行。本轮也重新读取了同一条目，历史使用与本轮复核均有记录。

**验证。** 颜色资源完整性、主题更新及 UI 作用域均有回归；指定手机深浅色隔离预览已通过。具体色值是项目设计选择，没有“从截图自动取色”或“官方一键配色”的过程。

证据：`暗色匹配。md:144`、`docs/WorkCheckpoint.md:91`；实现：`entry/src/main/ets/components/LowScoreEdgeLight.ets:156`。

### 4. 手机振动能力被误判为不可用

**现象。** 预览试振动时，代码对本地马达的能力判断不正确，不能正常进入短振请求。

**定位与修改。** 对照安装 SDK 的接口定义，改用无参数的 `vibrator.getVibratorInfoSync()` 默认查询；只选择 `isLocalVibrator` 的马达，使用其 ID 发出两次短振。保留80ms／120ms／80ms的请求设计、60秒冷却、取消第二下及失败不重试策略，并给出具体失败状态。

**验证。** 20组反馈回归通过；手机显示“两下已请求”，再次点击显示60秒冷却，设备日志可见相邻两次马达请求。

**Skill／知识库的贡献。** 原始日志确认10月14日11:13:54执行了下列检索，随后读取振动 API、SDK 的 `@ohos.vibrator.d.ts`，11:19:03修改服务，再运行回归及构建。这里能核实“先查文档与声明，再改查询方式”的顺序。

```sh
devecocli docs search "getVibratorInfoSync" "isLocalVibrator" --limit 5
```

手机接受请求不证明用户实际感觉到两下，也不证明硬件精确执行了设定间隔，这部分仍未验收。

证据：`docs/LowScoreReminder.md:91`；实现：`entry/src/main/ets/services/ReminderFeedbackService.ets:24`；回归：`scripts/verify-reminder-feedback.cjs:104`。

**实际错误。** 原始构建日志记录，10月15日17:45:58的 `CompileArkTS` 失败：

### 8. Git HTTPS 传输失败：依赖问题与网络问题分开解决

**第一层故障。** `git-remote-https` 报缺少 `libcurl.so.4` 和 `curl_global_trace` 等符号。`gh` 已登录且能访问 API，并不代表 Git 的 HTTPS pack 传输依赖正常。

**修复。** 经用户授权，通过包管理器安装匹配的 curl 及必要依赖；已有 OpenSSL4 同版本缺少 opt 链接，补齐链接。之后用 `curl --version`、`brew missing curl` 确认依赖状态。

**第二层故障。** 缺库修好后，原 DNS 解析地址连接超时。记录中通过官方 meta 来源核验可用地址并保持 TLS 主机校验，再用仅本次 Git 命令生效的 `http.curloptResolve` 完成实际 fetch，没有永久改 hosts 或全局 Git 配置。

**结果与归因。** 工作续接记录记载 fetch 成功，Git 历史确认10月15日已有0.2.8提交 `1e09f1f`；历史交付记录另记载该版已推送。本轮未重新查询远程，因此不新增“远程当前状态”结论。这是依赖及网络排查，没有证据说明由 ArkTS 技能或 HarmonyOS API 知识库直接修复。

证据：`docs/WorkCheckpoint.md:71`、`:194`。历史地址只作为当时处理记录，不应固化为长期网络配置。

### 9. 红边出现，但手环没有弹窗：查明正式通道的阻塞

**现象。** 用户实际守护时已看到手机红边，手环没有弹窗；此前独立的“10秒后发送”测试却能让手环显示并振动。

**怎么定位。** 先核对真实采样入口，确认低分反馈会提交到 `WearableReminderService`，并非简单漏接调用。再检查 `ready()` 的前提：用户开启、加载完成、前台状态、明确目标、设备支持和通道配置等。当前没有有效 `client_id`，服务申请仍待审批，通道无法就绪；手机上实际开关和目标通知能力本轮也没有读取。

**知识库提供的关键判断。** Wear Engine 是服务准入问题，普通手机通知权限不能代替。官方文档明确基本信息与消息通知的申请范围、Client ID 的配置位置、授权映射，以及批准后仍可能存在的资格缓存刷新。

**处理结果。** 解释并记录阻塞，保持默认关闭及明确状态，没有通过假 Client ID、修改评分或反复重试制造“已接通”。正式腕上通道与普通通知测试是两条不同路径；后者只在用户点击时发送，当前不消费正式低分事件。

这项是**定位完成、正式通道仍待条件**。后续需审批通过、真实身份与配置匹配、查询目标通知能力，再做真人守护验收。

### 10. 审批前如何验证手环：建立独立普通通知测试

**需要解决的问题。** 用户希望审批前就能实测本应用通知是否能到手环。既有 QQ 通知能振动，只能作为环境线索，不能作为坐直了已经成功的证据。

**知识库指导的实现。** 查询 Notification Kit 的普通文本通知、通知授权／渠道／请求结构，以及短时后台任务资料，新增独立设置入口：

1. 用户点击后检查手机通知权限；需要时请求授权，返回后再查询真实状态。
2. 使用有明确类型的通知内容与 `NotificationRequest`，通过 `notificationManager.publish` 发布一条自己的测试通知。
3. 提供立即发送与10秒后发送；延迟测试使用 `requestSuspendDelay` 的短时执行窗口，便于用户锁屏观察。

实际链路为：**坐直了手机普通通知 → 运动健康按用户现有设置同步 → 手环显示／振动**。它不调用 Wear Engine，也没有接入正式低分事件。

4. **把已复现的缺陷留成回归。** 如 setter-only Canvas、旧设置迁移、迟到回调、冷却与过期不补发。
5. **分别确认代码与设备。** lint、编译、桩测试检验代码；实屏范围、手机图库和手环振感需要对应设备或用户证据。
