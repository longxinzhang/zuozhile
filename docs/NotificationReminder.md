# 严重低分普通通知同步提醒

日期：2026-10-16。适用版本：坐直了 0.2.10。正式使用版变更与最新实测记录见 [NotificationRelease0210.md](NotificationRelease0210.md)；下方0.2.9验证表保留为历史。

用户反馈真实守护出现红色边缘但手环没有弹窗后，核对发现原正式通道仅为尚未配置 Client ID 的 Wear Engine，昨天通过的是独立手动普通通知测试。用户随后明确选择“增加普通通知自动提醒”，本次将原方案路线 B 接入正式严重低分事件，与 Wear Engine 路线 A 显式互斥。

## 使用步骤

1. 保持手环与华为运动健康连接。在手机系统通知设置中允许坐直了的通知和服务提醒渠道。
2. 在运动健康的设备消息通知中勾选坐直了，并选择“多设备提醒”或允许手机亮屏使用时提醒。守护长期在手机前台，只有锁屏时能同步的配置不足以完成自动提醒。
3. 停止守护后进入「设置 → 腕上提醒」，使用普通通知同步并开启腕上提醒。新安装默认这条路线；已有Wear Engine选择可手动切回普通通知，高级通道仍可显式选择。
4. 点击「准备手机通知权限与渠道」。必要时会显示系统授权框；准备操作不发送通知。可点「检查手机通知状态」重新检查。“就绪”仅表示手机通知权限及渠道可用，不表示手环在线或已收到。
5. 如需手动测试，展开同一区域的「测试与记录」并发送一条测试通知，分别观察手机通知中心、手环显示及实际振动，再选择用户确认。该测试与正式A/B提醒共用持久化10秒冷却，不启动相机或写坐姿统计；日常守护无需先测试。
6. 开始真实守护。只有既有调度器已确认三级且新有效样本当前分数仍低于50，才有普通通知发送资格；一级、二级也会有红色边缘，但不会触发腕上通知。
7. 持续严重低分期间，10秒是最短发送间隔，到期仍需等下一次有效低分采样；3秒采样下，发送条件持续满足时通常约12秒间隔，这不是实机送达时序结论。停止、恢复、后台、校准、数据失效或切换通道都不会补发旧事件。

腕上提醒仍默认关闭；0.2.10新设置、缺失或非法通道字段默认普通通知，已有合法A/B选择保持原样。安装升级不会替用户开启开关或修改系统/运动健康设置。已保存的普通通知路线在重开应用时会静默检查手机权限；通知权限被撤销或渠道不可用后，需手动准备，不在守护中弹授权框。

## 实现原理

```text
前台真实守护的新有效样本
  → 原有低分调度器确认三级，当前仍 <50
  → WearableReminderController 检查当前显式路线、TTL与共享10秒冷却
  → PhoneNotificationReminderChannel 检查手机通知权限及服务提醒渠道
  → 保存冷却后发布 Notification Kit 普通通知
  → 华为运动健康按用户配置同步到手环
```

普通通知路线不调用 Wear Engine，不需要其服务审批或 Client ID，不直接控制手环马达。同步目标由运动健康决定，本应用不枚举、指定或广播穿戴设备，也没有可靠的腕上送达回执。运动健康配置可能将通知同步到多台设备，不能当成 Wear Engine 的单目标通知。

普通通知使用应用自己的名称、固定 ID `29002` 和标签 `zuozhile-posture-reminder`。同一标识更新手机上一条通知，避免持续低分堆积；每次按新的严重事件发布，不设仅首次提醒。手机通知自动清除时间为发布时刻加60秒，手环副本的保留与清除由设备决定。

通知只含当前分数与原调度器给出的可靠建议，不含影像、关键点、基线、账号或穿戴设备标识。锁屏和手环可能显示这些文字。独立历史手动测试仍使用 ID `29001`，其清除按钮不会清除正式通知。

## 手机声音与振动

正式普通通知及其同区域测试通过 API 23 起可写的 `notificationFlags` 将 `soundEnabled`、`vibrationEnabled` 设为官方 `TYPE_CLOSE`（值2），仅削减本条通知额外的手机声音和振动。当前 SDK 的 `notificationManager` 未导出对应枚举，代码使用具名常量，字段仍由 `NotificationRequest` 提供类型上下文。

原手机短振开关、双短振时序、独立60秒冷却、光效与统计口径保留。不删除重建通知渠道，不修改用户铃声或勿扰，不通过额外马达调用补偿通知。

用户已对新版「设置 → 腕上提醒」B路线的单条测试明确回答手环“显示并振动”，证据来自改10秒前的安装版；对手机是否额外发声/振动回答“未留意”，因此手机无额外反馈仍未确认。屏幕状态未确认，也未确认真实严重低分自动守护闭环或10秒实机节流；不能用这次单条测试或旧的锁屏独立测试代替正式守护验收。

## 互斥、冷却和取消

- 路线 A/B 使用同一个控制器、发送锁和持久化10秒冷却；同区域的单条测试也共享冷却。切换路线、开关、会话、页面、设备或清除诊断都不重置冷却。
- 只调用当前所选通道。A 未配置、超时或失败不自动改走 B；B 失败也不改走 A。用户切换路线仅作用于之后的新事件。
- 候选有效期仍为原有数据过期时间与创建后5秒的较早值。每个异步边界和真正发布前复查前台、会话、守护、校准、最新分数、路线及单调时钟有效期。
- 发布前先保存冷却；保存失败不提交，存储等待不抵扣从SDK实际提交时刻起算的10秒间隔。SDK发布请求超时后标记结果未知，原 Promise 未落定前继续锁定发送槽，防止不可取消的请求并发或自动补偿。
- 通知/渠道检查失败后撤销手机侧就绪状态，停止每帧盲目重试；需手动重新检查或准备。若只因切页或开始守护取消尚未返回的被动检查，保留此前就绪；此前尚未确认时，允许之后的新有效严重事件重新静默检查一次，不复活旧候选。授权只由用户点「准备」触发，授权成功后也复查实际通知许可和上下文。
- 已交给系统的通知不能保证撤回。停止守护、返回前台、重连、权限恢复和冷却结束都不会发送积压通知，也不能据手机发布成功填写腕上收到或振动确认。

## 与历史独立测试的区别

「设置 → 开发者工具 → 手机通知同步测试」是此前用户亲测通过的独立诊断入口，支持立即或10秒后发送，不消费严重事件，仍有独立60秒冷却，允许用户明确安排锁屏后测试。它不自动开启本功能；其普通通知也未采用本次正式提醒的静音标志。

本次「腕上提醒 → 普通通知同步」消费真实严重低分，只有前台守护可发送；同区域测试与正式A/B共用10秒冷却。两者的结论、通知ID、统计及异步条件不能混用。历史原理和结果见 [NotificationSyncTest.md](NotificationSyncTest.md)。
