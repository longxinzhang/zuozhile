## 本轮实现边界

| 范围 | 处理 |
| --- | --- |
| 通知路线 | 用户显式选择 A（Wear Engine模板通知）或 B（普通通知经运动健康同步），两路互斥，不需要对应腕上应用 |
| 无能力或失败 | 保留原手机行为，不自动换通道或双发补偿；选择 B 后只由新有效严重低分触发普通通知 |
| 检测与评分 | Camera、Core Vision、嘴部识别、评分公式和阈值保持不变 |
| 校准与采样 | 个人基线、校准规则、灵敏度及 2/3/5 秒抽帧保持不变，不增加采样或推理 |
| 正式提醒资格 | 前台、真实守护、非校准，新有效样本经既有调度器确认三级且本次分数仍 `<50` |
| 手机反馈 | 光效、减少动态、短振开关及手机双短振60秒冷却独立保留，腕上调用不阻塞采样 |
| 业务统计 | 沿用 0.2.8 口径，不因腕上请求、回调或手机与腕上同时反馈额外累计 |

既有 `<70 / <60 / <50` 的独立持续确认、至少 6 秒及两次有效采样、`73 / 63 / 53` 恢复滞回不变。腕上不另建评分状态机，不直接按单帧低分发送，不把 `decision.vibrate` 或 `visualEvent` 当发送条件；50–52 分滞回停留三级时不重复发腕上提醒。

首版只发送严重低分的精简分数与可靠建议；没有可靠原因时用“请调整坐姿”。不向穿戴设备发送相机影像、脸部/骨骼关键点或校准基线，不接入 Health Kit 健康数据，不新增后台相机、后台守护、腕上 App 或远程校准。

## 冷却与异步规则

- 腕上独立 10 秒持久化冷却，与手机双短振60秒冷却互不替代；跨页面、会话、A/B路线、设备切换及开关共享，同区域测试与正式也共用这一冷却。调用 SDK 前占用发送槽与冷却，失败、超时均不重试。
- 进程内按单调时间计算冷却，本地仅保存必要的最近尝试时间以保守恢复；重启、时间回拨或异常时间不得形成连发或永久禁用。清除诊断不清冷却。
- 候选本地 TTL 取 `min(既有 expiresAt, 候选创建后 5 秒)`。5 秒是防陈旧的本地设计值，不是平台送达或腕上显示时限承诺；异步设备查询、能力检查返回后及真正发送前重查有效期、会话、前台、开关和最新分数。
- 冷却中、断连、无能力、候选过期或服务不可用时直接丢弃，不排队。冷却结束、重连、前台恢复和服务恢复都不补发旧事件，正式提醒仍须等待新的有效严重低分样本。
- 停止守护、校准、无效数据、后台、页面销毁、关闭开关或切换目标时使旧代次失效，取消未提交待办。已交给系统的通知不能保证撤回；超时标记“结果未知”，迟到回调只记对应诊断，不能恢复守护、改分或追写业务统计。
- A只向用户明确选择的一台在线且支持通知的设备发送，不广播、不默认取列表第一台。连接 `randomId` 仅在内存作路由，不写 Preferences、诊断或业务记录；重连后重新枚举，标识变化或目标有歧义时要求重选，不读取 SN 代替。B的同步目标由运动健康设置决定，不检查或宣称手环在线、能力或送达。
- A查询或发送失败后清除当前选择，需手动刷新、重选；B查询或发送失败后清除手机侧就绪，需手动检查或准备，不会在每次新采样中盲目重复失败的查询。仅因切页/开始守护取消的被动检查可由之后的新有效严重事件再次静默检查，不恢复旧候选。发送Promise超时后发送槽仍锁定，直到原Promise落定，避免不可取消请求重叠。
- 发送前先串行持久化冷却；保存失败不提交SDK。存储等待不抵扣从SDK实际提交时刻起算的10秒间隔。保存时预留候选剩余TTL作为保守上界，重启恢复可能比实际发送多等至多约5秒；异常时最多保守等待10秒，页面重建不反复延长同一异常记录。
- 本次仅将正式A/B及同区域单条测试的共享冷却改为10秒；历史独立「手机通知同步测试」（ID `29001`）仍为60秒冷却，正式B通知的自动清除时间仍为发布后60秒，手机通知授权超时仍为60秒。

## 测试与诊断

入口位于设置的腕上提醒区域，延续现有设置页面，不增加首页卡片或底部 Tab。A当前无 `client_id` 时保持“待配置”。B需主动准备手机通知许可和渠道，其“就绪”仅代表手机侧可发布；不靠普通通知同步结果宣称Wear Engine就绪。

手动测试必须由用户主动点按，只发一条；与正式守护互斥，守护中或校准中不可测试，测试待办遇到守护启动或上下文失效即取消。测试不启动相机、不改分数或基线，不进入采样次数、提醒次数与会话报告，但遵守腕上同一 10 秒冷却。

最近测试区分“发送请求成功”“失败/结果未知”和用户手动确认。三项确认固定为：

- 收到并振动。
- 只收到通知。
- 没收到。

尚未选择时保持“尚未确认”。Promise resolve、设备动作回调或点“知道了”都不等于用户看到了通知、感到了振动或姿态已恢复；不得由代码自动代填确认。

诊断最多 100 条、最长 24 小时，仅本地，独立于 `SessionRecord` 与业务统计。记录最少的事件、测试标记、请求/API 结果、必要错误码和用户确认；不保存完整通知正文、图像、关键点、基线、连接 `randomId`、稳定硬件标识、原始账号或凭据。提供清除入口，不自动上传或导出。

## 官方服务准入

### AGC 申请与用户选择

官方服务审批是 AppGallery Connect（AGC）的 Wear Engine **服务准入**，不是手机 runtime 健康权限，也不是反复弹用户授权框可以解决的问题。

1. 开发者登录 AGC，在“开发与服务”选择对应项目与 HarmonyOS 应用，经“项目设置 → 开放能力管理 → Wear Engine → 管理”进入申请流程。
2. 最小范围只申请“设备基础信息 + 消息通知”。官方 `wearengine_apply` 明确个人开发者可申请这两项基本能力；可申请不表示本应用已获批准，审核结果与时间不能预先承诺。
3. 按控制台要求提交真实的数据使用说明及用户授权/操作路径材料，等待审批；本轮没有代为申请、同意协议或提交材料。

“设备基础信息”和“消息通知”在此 HarmonyOS 路线下不另要求对应的 SDK 用户授权；服务审批、用户主动启用产品功能、用户明确授权设备测试是不同层次。不要为模板通知索取 `USER_STATUS`、健康/运动传感器、心率、位置、设备序列号权限，或照搬 Android 的 `Permission.NOTIFY`。勿扰与佩戴由用户后续确认，不据无权限读数宣称状态。

### Client ID 与签名

- 当前尚无 `client_id`，不填假的或占位值使服务看似配置完成，也不把 APP ID 当成可互换的 Client ID。
- 后续从 AGC 对应应用取得真实 Client ID，按官方 `configuration_client_id` 放入 `entry/src/main/module.json5` 的 `module.metadata`，条目名为 `client_id`；当前未编辑该文件或签名配置，应用版本已单独更新为0.2.9。
- 应用包名 `com.longxin.zuozhile`、实际安装签名与 AGC 服务登记身份必须匹配。遇到不匹配先报告具体项，不自动改包名、换签名或重建身份。
- 本路线不要求提供 Client Secret、私钥、签名密码或账号令牌；不向用户收集 secret，不在诊断、源码或文档中记录凭据。

### 资格缓存

官方 `wearengine_faq-3` 提示：审批前调用失败后，未申请资格记录可能仍被缓存，每 24 小时自动刷新一次。先核对申请已批准、申请范围及应用身份；未申请/未批准不能解释成“只等缓存即可接通”。

本项目不通过清空数据、卸载重装华为运动健康或改身份绕过缓存。批准后仍遇同类错误时，记录不含凭据的错误与时间，等待自动刷新并在用户授权范围内复核；仍未恢复再向官方提单。不得破坏用户健康数据、配对或设置来缩短等待。

## 批准后的验证顺序

以下均为后续计划，未执行，不自动沿用 0.2.8 的设备或测试授权。

1. 先取得所需服务批准，核对真实 Client ID、包名与签名；配置变更后重跑 lint、全部离线回归及构建。无批准时只记录阻塞，不部署试通道。
2. 型号/固件、配对、运动健康消息通知及QQ通知振动已获用户确认；继续核对运动健康版本、Wear Engine在线连接、账号与隐私准备、勿扰/佩戴/振动条件。系统设置如需改变，先取得同意并约定恢复，不自动关闭勿扰。
3. 取得明确的目标手机、手环及测试授权后，才查询在线设备与 `NOTIFICATION`，明确选一台，主动发送一条测试，分别记录 API 结果、腕上实际显示及三项手动确认。

5. 阶段 1 另做指定手机安装启动与真人正式守护闭环，覆盖新有效三级、冷却、恢复、无效数据、停止/后台、断连及不补发，并确认手机行为与业务统计不变。仅设置页、隔离预览或桩测试不算通过。

不保证强制亮屏、绕过勿扰、复制手机两下短振或所有华为穿戴通用；显示、振动和响应延迟均须实测，长期稳定性与功耗另行记录。
